# Working with AI agents

> 🇪🇸 [Versión en español](./working-with-agents_ES.md)

This is the chapter that explains how one person wrote 318,000 lines, 44 specifications and 491 test files in 52 days. It is not a list of tools: it is a contract, a catalogue of reusable skills and an adversarial review process.

---

## 1. The contract: `AGENTS.md`

At the root of the repository sits a 150-line document that defines how agents must work. It is not a style guide: it is the project contract, and it is written in the imperative.

Its quick rules set the frame: follow the spec-driven cycle for any product or code change, follow strict TDD in implementation, keep architectural boundaries intact because *"dependency direction is not negotiable"*, prefer existing patterns over inventing abstractions, keep changes small and reviewable, and do not open a pull request until tests, types, dependency guards and architecture guards all pass.

It then develops seven sections: repository shape, cycle flow, TDD contract, clean architecture rules, security by design, frontend and design system rules, dependency policy, file discipline and agent behaviour.

### The interesting parts are the rules that correct a specific behaviour

A contract written up front would be a list of good intentions. This one bears the marks of having been written **after watching an agent get something wrong**.

Thirty lines are devoted to a single TypeScript package export condition, explaining why it must be called `source` and never `development`: because Turbopack activates `development` and would resolve the source barrel, whose specifiers it cannot map back, breaking any client component that imports a runtime value. Nobody writes that out of caution; you write it after losing an afternoon.

There is a rule requiring the English and Spanish catalogues to be updated **in the same change**, with a parity test that checks it. It exists because the alternative is a half-translated interface.

And there are three behavioural rules that are worth the whole document: *"Never fabricate test results. If a command was not run, say so"*, *"Never commit without explicit user approval"* and *"Never add AI attribution or Co-Authored-By lines to commits"*.

The first is the most important. An agent that claims to have run a suite it never ran is worse than an agent that runs nothing at all, because it destroys the only reliable signal the reviewer has.

### The closing checklist

The document ends with nine boxes to confirm before calling anything done: cycle artifacts up to date, tests written first with their edge cases, type checking, tests, architecture, dependency guard, build, review of security implications and tenant isolation, and use of design system primitives.

Turning the definition of "done" into an explicit list is what stops it from eroding under fatigue.

## 2. The tooling

| Tool | Function |
|---|---|
| **gentle-ai** | Agent orchestrator: cycle phases, subagent delegation, skill registry, persistent memory and model routing |
| OpenCode | The agent environment the development ran on |
| `openspec` | Spec-driven cycle artifacts and their archive |
| Open Design via MCP | Visual source of truth: the design is synced from the service before touching any interface |
| `.codegraph` | Code index for agent navigation and querying |
| `.atl/skill-registry.md` | Catalogue of reusable skills, generated by gentle-ai |

### gentle-ai, the orchestrator

The piece that holds up everything else is [gentle-ai](https://github.com/Gentleman-Programming/gentle-ai), an ecosystem configurator written in Go and released under the MIT licence that turns a coding agent into a collaborator with memory and a workflow, instead of leaving it as a chat that writes files.

It contributes four things this project used intensively.

**Phase orchestration with isolated context.** Each phase of the spec-driven cycle runs in its own context window through subagent delegation: the orchestrator coordinates and the subagents execute. It is exactly the pattern that makes a seven-phase cycle viable without the context degrading halfway through.

**Explicit delegation criteria.** Delegation is not decided by intuition: it fires when the work demands broad exploration, implementation across several files, running tests or builds, or adversarial review with fresh context. That last condition is where Judgment Day comes from.

**Skill registry.** This repository's `.atl/skill-registry.md` file is generated by gentle-ai, which scans the skill directories of the various installed agent environments. That is where the twelve catalogued skills come from, including `chained-pr`, `work-unit-commits` and `judgment-day`.

**Persistent memory across sessions and across agents**, via Engram, its memory protocol, so that decisions taken in one session remain available in the next and across different tools.

### The skill registry

This is the least obvious piece and one of the most interesting. The repository maintains a generated index of the available skills — twelve as of the last update, on 9 August — by scanning eight different agent tool directories.

Its contract is written out explicitly and it is subtle: *"Delegator use only. This registry is an index, not a summary"*. An agent about to launch subagents reads the index, selects the relevant skills and **passes the exact paths** so that the subagent reads the full document. The reason is stated: do not inject generated summaries, so that the subagent loads the contract in full and the author's intent is preserved.

Put another way: the temptation to compress the instruction is resisted, because compressing is interpreting and interpretation is lost at every hop.

Among the registered skills there are several that say a lot about the method: `chained-pr` fires on pull requests over four hundred lines and splits them into a chain to protect the reviewer's focus; `work-unit-commits` plans commits as reviewable units, keeping tests and documentation alongside the code; `cognitive-doc-design` writes documentation designed to reduce cognitive load.

## 3. Judgment Day: blind adversarial review

The most distinctive skill is called `judgment-day`, it is part of the phase agents that gentle-ai installs, and it is described as blind dual adversarial review with a maximum of two bounded rounds of correction and re-judgement.

It works the way the name suggests: several independent judges review the same work without seeing each other, actively hunting for the flaw. What makes the mechanism credible is that it **left a trail in the repository**, and that trail is in the change documents, not in a marketing report.

Four documented corrections from the offline operation change carry the label "Judgment Day PR4 correction":

The **reentrancy guard on queue flushing**, because `flush()` is invoked from three independent triggers and, with no mutual exclusion, overlapping fires broke the sequentiality invariant.

The requirement that **discarding a poison message be surfaced to the user**, because the original implementation deleted it exactly as it would a synchronised mutation, with no signal in the interface whatsoever. It was a data integrity defect dressed up as a presentation detail.

Deriving **the local store's identity key from the tenant-user pair rather than from the session token**, because the token rotates on every sign-in — so users were auto-purging their own queue — and because the hash of that token is the API's internal correlator, whose exposure to the client is a needless leak.

And **separating the expired session from the generic 4xx error bucket**, because it was causing perfectly valid mutations to be discarded.

There is also evidence of two rounds over the memory write gate, and of a judgement cutting across an entire feature, with a correction round applied and approval confirmed.

**All four defects are of the kind a green test does not catch.** None of them broke an assertion: they broke a guarantee. That is exactly the gap an adversarial review covers and a test suite does not.

## 4. How the work actually divided

It is worth saying plainly, because it is the question underneath everything.

The agents wrote most of the code, the tests and the change documents. The person did four things the agents could not do: decide what to build and in what order, write and refine the contract that governs the agents, review and approve every pull request, and arbitrate when adversarial review turned something up.

The limit of the method is that fourth activity. You can delegate the writing; you cannot delegate the judgement. That is why the average pull request is twelve files and not a hundred and twenty: because the bottleneck is one person's capacity to genuinely review, and the method is designed around that constraint instead of ignoring it.

## 5. What makes this work

Three conditions, and all three are necessary.

**An explicit, maintained contract.** `AGENTS.md` was not written once: it grew with every unwanted behaviour that had to be corrected. A contract that is not updated stops governing.

**Automated guards that do not depend on attention.** Type checking, tests, architecture, dependencies, interface against API, build and coverage. They are detailed in [quality and guards](./quality-and-guards.md). Delegating volume without an automated net is delegating risk.

**A process that actively hunts for the flaw.** Tests check what it occurred to you to check. Adversarial review looks for what did not occur to you. At high volume, the second matters more than the first.
